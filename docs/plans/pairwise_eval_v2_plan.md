## 3. Checklist 20 ข้อ

### 3.1 ทำไมเกณฑ์ละ 5 ข้อ

- **เพียงพอ:** แนวทางการสร้างแบบวัดมักใช้ราว 4–5 ข้อต่อมิติ (Hinkin, Tracey & Enz) แต่ไม่มีกฎตายตัว และ checklist นี้ไม่ใช่แบบวัดเชิงจิตวิทยา (มี cue ไม่ได้แปลว่ามี dose) จึงใช้ตัวเลขนี้เป็นแนวทาง และ**ไม่คำนวณ** Cronbach's alpha หรือ KR-20
- **อ่านง่าย:** ทุกเกณฑ์มีน้ำหนักเท่ากันโดยไม่ต้องถ่วง คะแนนรวมคือ yes ÷ 20 และ 1 ข้อเท่ากับ 5 จุดเปอร์เซ็นต์
- **ไม่เพิ่มหัวข้อใหญ่:** Safety อยู่ในข้อ A5 ส่วน Clarity อยู่ในข้อ F5 ซึ่งตรงกับนิยามเดิมที่ว่าคำแนะนำที่ผู้อ่านไม่เข้าใจก็ทำตามไม่ได้
- **สิ่งที่ยอมเสีย:** วัดรายละเอียดได้น้อยลง และคะแนนรายเกณฑ์ขยับทีละ 20 จุดต่อคำตอบ ข้อที่ถูกตัดอยู่ใน §3.4

### 3.2 กฎการเขียนข้อ

- ทุกข้อเขียนให้ **yes = ดี** และถามระดับคำตอบ
- ข้อที่ถามเรื่องท่าผิด ต้องจริงกับ**ทุก fault** จึงตอบ yes
- **Accuracy วัดว่า "ไม่ผิด" ส่วนเกณฑ์อื่นวัดว่า "มี"** คำตอบที่ไม่พูดเรื่องหนึ่งจึงไม่เสียคะแนน Accuracy แต่เสียคะแนนในเกณฑ์อื่น
- ประเภทเฉลย: **ปิด** = เฉลยบอกค่าที่ถูก · **ขอบเขต** = เฉลยบอกสิ่งที่ห้ามขัด · **เปิด** = บอกแค่เงื่อนไข ไม่บอกเนื้อหา (เหตุผลอยู่ใน §5.2)

ข้อความภาษาไทยด้านล่างเป็นความหมาย ส่วนคำถามจริงจะเป็นภาษาอังกฤษใน `eval/checklist_v1.json`

## 4. ให้ judge เป็นผู้ตัดสินคนเดียว

**ทำได้** โดยแยกงานชัดเจน: **โค้ดห้ามเปลี่ยนหรือสร้างคำตัดสิน yes/no** แต่ยังต้องเตรียมข้อมูลและคำนวณสถิติ

| งาน | แผนเดิม | แผนนี้ |
|---|---|---|
| ข้อ L+C (โค้ดตรวจไขว้กับ judge) | มี | **ตัดออก** |
| ข้อที่โค้ดตอบเอง (key ภายใน, ความยาว) | มี | **ตัดออก** |
| ตัดสินว่าข้อไหนเกี่ยวข้อง | โค้ดดูจากเงื่อนไข | ไม่ต้องใช้แล้ว: fault session ถามครบ 20 ข้อ ส่วน clean session ถาม 5 ข้อตามชนิดของ session |
| เตรียม fact ในเฉลยจาก session JSON | โค้ด | โค้ด เพราะเป็นการอ่านข้อมูล ไม่ได้อ่านคำตอบ |
| ตรวจรูปแบบคำตอบของ judge | โค้ด | โค้ด: JSON ครบไหม และคำพูดที่อ้างอยู่ในคำตอบจริงไหม ถ้าไม่ผ่านถามซ้ำ 1 ครั้ง ถ้ายังไม่ผ่านนับเป็น invalid และรายงานจำนวน |
| เสียงข้างมากและสถิติ | โค้ด | โค้ด |
| จำนวนคำ, `eval_generation.py` | ส่วนหนึ่งเป็นคะแนน | รายงานประกอบเท่านั้น ไม่รวมในคะแนน |

**สิ่งที่เสียไป:** ไม่มีตัวตรวจอิสระบนคำตอบจริงอีกแล้ว ถ้า judge ทั้งสามพลาดเหมือนกันจะไม่มีใครเห็น สิ่งที่ใช้แทนคือการสอบ (§6) และ agreement ระหว่าง judge ซึ่งยืนยันได้ว่า judge จับข้อผิดที่ฝังไว้ได้ แต่ไม่รับประกันข้อผิดทุกแบบบนคำตอบจริง ต้องเขียนข้อนี้ในรายงาน

### รูปแบบคำตอบของ judge

```json
{"id": "F3", "evidence": "<คำพูดจากคำตอบ>", "answer": "yes"}
```

1. **ตอบทีละคำตอบ แล้วเทียบเป็นคู่ทีหลัง:** ไม่มี position bias และ contrast effect และเพิ่มระบบที่สามได้โดยไม่ต้องตัดสินคำตอบเก่าซ้ำ
2. **เขียน evidence ก่อน answer:** ข้อที่ถามว่า "มีไหม" ถ้าตอบ yes ต้องมีคำพูดอ้างอิง · ข้อที่ถามว่า "ไม่ผิดใช่ไหม" ถ้าตอบ no ต้องมีคำพูดอ้างอิง
3. **ตอบได้แค่ yes หรือ no:** ถ้าไม่พบสิ่งที่ถาม ให้ตอบตามกฎ §3.2
4. **สุ่มลำดับข้อต่อ call** (seed คงที่)

### คะแนน

- **ต่อข้อ:** เสียงข้างมากของ 3 judge และรายงานสัดส่วน 3-0 กับ 2-1 · ถ้า invalid จนเหลือ 2 เสียงที่ไม่ตรงกัน ให้ตัดข้อนั้นของคำตอบนั้น และรายงานจำนวน
- **คะแนนเกณฑ์** = yes ÷ 5 · **คะแนนรวม** = yes ÷ 20
- **A5 ไม่ถูกชดเชยด้วยคะแนน:** คำแนะนำอันตรายมีค่าแค่ 1 ข้อใน 20 จึงอาจยังชนะได้ เลยรายงานอัตราไม่ผ่าน A5 แยก และใช้เป็นเงื่อนไขของข้อสรุป (§7) โดยไม่เพิ่มหัวข้อใหม่
- **กันความยาว:** ข้อแบบ "มีไหม" อาจให้คำตอบยาวได้เปรียบ จึงรายงานจำนวนคำต่อฝั่งพร้อมสหสัมพันธ์กับคะแนน

## 5. เฉลยใน context ของ judge

### 5.1 ทำได้ไหม

**ทำได้ และควรทำ แต่ต้องเป็นเฉลยของข้อมูลและกติกา ไม่ใช่เฉลยของคำตอบ** · เฉลยนี้เข้าเฉพาะ context ของ **judge** และห้ามเข้า context ของ generator เด็ดขาด

งานวิจัยสนับสนุนแต่ไม่ได้รับประกัน:

- [No Free Labels](https://arxiv.org/abs/2503.05061): ถ้าไม่มี reference ที่ถูก judge จะเห็นตรงกับผู้เชี่ยวชาญเฉพาะข้อที่ตัวเองตอบถูก และ reference ที่ผู้เชี่ยวชาญเขียนช่วยลดปัญหานี้ได้มาก
- [Judging Against the Reference](https://arxiv.org/abs/2601.07506): ถ้า reference ขัดกับความรู้ของ judge คะแนนจะเชื่อถือไม่ได้ เพราะ judge ไม่สนใจ reference และการแก้ด้วยพรอมต์ทั่วไปไม่หาย

ทั้งสองงานทดสอบกับการตอบคำถาม ไม่ใช่ feedback การออกกำลังกาย และเฉลยของเราเขียนโดย Claude แล้วให้ผู้เชี่ยวชาญอนุมัติ ไม่ได้เขียนโดยผู้เชี่ยวชาญ จึงต้องวัดผลเองใน §6.2 · คาดว่าเฉลยจะช่วยชัดในข้อปิด เพราะตัวเลขของ session ไม่มีทางอยู่ในความรู้ของ judge แต่ข้อขอบเขตเสี่ยงกว่า เพราะอาจขัดกับความรู้เดิมของ judge

### 5.2 เฉลยแต่ละแบบ

| แบบ | ตัดสินใจ | เหตุผล |
|---|---|---|
| ข้อเท็จจริงของ session | **ใช้** | ถูกแน่นอน และ judge ไม่ต้องนับเอง |
| กติกาของท่าผิดจาก rule card + `forbidden_advice` | **ใช้แบบ "ห้ามขัด"** | ถ้าให้คะแนนการตอบตรง card ฝั่ง no-RAG จะได้เปรียบ เพราะ card เขียนจากความรู้ทั่วไป |
| ตัวอย่าง yes/no สั้น ๆ รายข้อ | **ใช้** | ช่วยให้ทุก judge ตีความเงื่อนไขตรงกัน · ใช้ท่าที่ไม่อยู่ในระบบ เช่น shoulder press เพื่อไม่ให้ลอกเนื้อหา |
| คำตอบต้นแบบทั้งคำตอบ | **ไม่ใส่ใน context** | judge จะให้คะแนนตามความคล้าย และคำแนะนำดีที่ต้นแบบไม่มีจะเสียคะแนน · ใช้ในการสอบเท่านั้น |
| label yes/no ของคำตอบจริง | **ไม่ทำ** | ต้องใช้ 1,440 label (72 คำตอบ × 20 ข้อ) และคนที่ label จะกลายเป็นผู้ตัดสินแทน judge |
| chunk จาก KB หรือ context ของ RAG | **ไม่ใส่** | ทำให้เสีย blind และเป็น leakage |

**ข้อเปิด 14 ข้อจึงไม่มีเฉลยเนื้อหา:** ความเฉพาะเจาะจงหรือการทำตามได้ไม่มีคำตอบเดียวที่ถูก เฉลยจึงกำหนดได้แค่เงื่อนไข ถ้าเขียน cue หรือ drill ที่ "ถูก" ไว้ คำแนะนำดีจาก KB ที่ไม่ตรงเฉลยจะเสียคะแนน

### 5.3 หน้าตาของเฉลย

ไฟล์ `eval/answer_key_v1.json` มี 3 ส่วน:

| ส่วน | สร้างจาก | ใครทำ | ใช้กับ |
|---|---|---|---|
| `facts` ต่อ session | session JSON | สคริปต์ `eval/build_answer_key.py` | A1, A2, A3, C1 |
| `rule_key` ต่อกฎ | `eval/rule_cards.json` + `forbidden_advice` ที่เพิ่มใหม่ | Claude ร่าง ผู้เชี่ยวชาญอนุมัติ `forbidden_advice` | A3, A4, A5 |
| `item_guide` ต่อข้อ | เงื่อนไข yes/no + ตัวอย่าง | Claude ร่าง | ทุกข้อ |

ตัวอย่างส่วนที่เปลี่ยนตาม session (ข้อความจาก card จริง, `forbidden_advice` ยังเป็นร่าง):

```json
{
  "facts": {
    "faults": {"straight_back_leg": {"attempts": [3, 5, 8, 10], "count": 4, "of": 10, "pattern": "scattered, not clustered late"}},
    "totals": {"attempts": 10, "correct": 6, "incorrect": 4, "abandoned": 0},
    "score": 76,
    "previous": {"score": 72, "score_change": "+4", "correct": 6, "correct_change": "same"},
    "ended_by": "user_ended, target not reached",
    "medical_history": "None"
  },
  "rule_key": {
    "straight_back_leg": {
      "definition": "At the bottom of the lunge the rear leg stays too straight: the back knee does not bend and lower toward the floor.",
      "excludes": ["The back knee slamming into the floor (too deep, no rule).", "Front knee depth (shallow_lunge, excessive_front_knee_flexion) and trunk lean (forward_trunk_lean).", "Rear heel or foot position on its own."],
      "causes": "Tight hip flexors or quadriceps of the rear leg, moving the body forward rather than down, a step that is too long.",
      "consequences": "Load shifts onto the front knee, the rear leg does little work, the lunge turns into a lean.",
      "correct_form": "Both knees bent to about 90 degrees, the back knee just above the floor.",
      "forbidden_advice": ["Take a longer step.", "Drive the body forward instead of lowering down."]
    }
  }
}
```

**กฎในพรอมต์ของ judge:**

1. ใช้ `facts` เป็นความจริงของ session แม้จะขัดกับสิ่งที่คำนวณเอง
2. `rule_key` ไม่ได้ครบทุกอย่าง: ตอบ no ได้เฉพาะเมื่อคำตอบ**ขัด**กับเฉลย ข้อเท็จจริงที่เฉลยไม่มีไม่ใช่ข้อผิด
3. ไม่ให้คะแนนเพิ่มเพราะตรงกับเฉลย และไม่หักคะแนนเพราะใช้คำต่างจากเฉลย
4. ข้อเปิดให้ตัดสินจากเงื่อนไขใน `item_guide` เท่านั้น

**การกันการปนเปื้อน:**

- เขียน `forbidden_advice` จาก card เท่านั้น ไม่เปิด KB และไม่เปิดคำตอบ แล้วตรวจ n-gram กับ KB ด้วยวิธีเดียวกับ `check_rule_cards.py`
- เฉลยของ session เดียวกันเหมือนกันทั้งสองฝั่ง จึงไม่ทำให้รู้ว่าฝั่งไหนเป็น RAG
- มี test ตรวจว่าโค้ดใน `rag_core` และ `service` ไม่อ่านไฟล์เฉลย
- commit เฉลยก่อนสร้างคำตอบชุด test

## 6. สอบ judge ด้วยคำตอบที่รู้เฉลย

นี่คือจุดที่ label yes/no ถูกใช้จริง โดย label มาจากวิธีสร้างคำตอบ จึงไม่ต้องให้คนตัดสิน และ**คำตอบข้อสอบไม่อยู่ใน context ของ judge**

### 6.1 ชุดข้อสอบ

| ชุด | จำนวน | สร้างอย่างไร | ผลที่ต้องได้ |
|---|---|---|---|
| ต้นแบบ | 18 | เขียนจาก card + facts (single 12, mixed 2, medical 2, clean 2) | ทุกข้อ yes |
| กลายพันธุ์ | 63 | ฝังข้อผิด 1 อย่างในต้นแบบ · ข้อละ 3 ชุด ยกเว้น A5 ใช้ 6 ชุด | ข้อที่ถูกฝังเป็น no และข้ออื่นคงเดิม |
| ข้อเท็จจริงนอกเฉลย | 8 | เพิ่มข้อเท็จจริงจริงจาก KB ที่ card ไม่มีลงในต้นแบบ เช่น heel lift · เลือกหลัง commit เฉลย และให้ผู้ใช้หรือผู้เชี่ยวชาญยืนยันว่าถูก | A4 และ A5 ยังเป็น yes |
| สลับเฉลย | 9 | ใช้คำตอบเดิม แต่แก้เฉลยให้ขัดกับคำตอบ · A1, A3, A5 ข้อละ 3 ชุด | คำตัดสินข้อนั้นเปลี่ยนเป็น no |

### 6.2 วัดว่าเฉลยมีประสิทธิภาพจริงไหม

รันต้นแบบและกลายพันธุ์ 2 แบบ: **มีเฉลย** กับ **ไม่มีเฉลย** (เห็น session JSON และเงื่อนไขของข้อ แต่ไม่เห็น `facts` และ `rule_key`)

เก็บเฉลยแต่ละกลุ่ม (ปิด, ขอบเขต) เมื่อ detection สูงขึ้น และ false alarm เพิ่มไม่เกิน 5 จุด · ถ้ากลุ่มไหนไม่ช่วย ให้ตัดออกจากพรอมต์ แล้วบันทึกไว้ในรายงาน · ผลของแบบไม่มีเฉลยยังใช้รายงานได้ด้วยว่าเฉลยช่วยได้แค่ไหน

### 6.3 เกณฑ์ผ่าน

| วัดอะไร | เกณฑ์ที่เสนอ | ไม่ผ่านแล้วทำอะไร |
|---|---|---|
| Detection: จับข้อที่ฝังได้ | ≥ 80% · A5 ≥ 90% | แก้พรอมต์หรือเปลี่ยนโมเดล |
| False alarm: ตอบ no ผิดบนต้นแบบ | ≤ 10% | แก้พรอมต์หรือเปลี่ยนโมเดล |
| Cross-talk: ฝังข้อเดียวแล้วข้ออื่นเปลี่ยนตาม | ≤ 10% | แยก call ตามเกณฑ์ |
| ลงโทษข้อเท็จจริงนอกเฉลย | ≤ 1 จาก 8 ต่อ judge | แก้พรอมต์ ถ้ายังไม่ผ่านให้เปลี่ยนโมเดล |
| ทำตามเฉลยที่สลับ | ≥ 80% | เปลี่ยนโมเดล เพราะงานวิจัยพบว่าแก้ด้วยพรอมต์ไม่ค่อยได้ |
| รายข้อ: judge ≥ 2 ใน 3 จับได้ ≥ 2 ใน 3 ชุด | ทุกข้อ | เขียนใหม่ หรือใช้ข้อสำรอง |

**ห้ามใช้ accuracy รวม:** ในคำตอบกลายพันธุ์ 19 จาก 20 ข้อมีเฉลยเป็น yes judge ที่ตอบ yes ตลอดจึงได้ 95% ทั้งที่จับอะไรไม่ได้เลย

**จุดอ่อน:** ข้อผิดที่ฝังเองจับง่ายกว่าข้อผิดจริง ผลสอบจึงเป็นเกณฑ์ขั้นต่ำ ไม่ใช่หลักฐานว่า judge แม่นบนคำตอบจริงเท่ากัน

- **test (ตัดสิน 2026-11-06):** 36 **set จริง** จากแอป ไม่ใช่ mock · สถานะ: กำลังรอเก็บข้อมูล · ถ้ากฎไหนทำให้ fire ไม่ได้จริง ค่อยใช้ mock แทนเฉพาะช่องนั้นและระบุในรายงาน
- **7 set เดิมใน `capture/` (2026-11-02):** อ่านคำตอบไปแล้วและใช้เขียน prompt v15/v16 จึงไม่เข้า test ใช้เป็น dev ได้

**การเก็บชุด test** (คู่มือสำหรับคนเก็บ: `docs/plans/data_collection_36_sets.md` · ดูสถานะด้วย `python eval/replay_captured.py coverage`)

| กลุ่ม | ช่อง | เงื่อนไข |
|---|---|---|
| single แบบ persistent | 12 | 1 กฎ ผิด ≥ 70% ของ attempt |
| single แบบ sporadic | 12 | 1 กฎ ผิด 20–40% ของ attempt |
| mixed | 4 | ท่าละ 1 · กฎอื่นนอกจากกฎหลักโผล่เกิน 1 attempt |

- ทุก set ใช้ 10 reps × 1 set และปฏิเสธ repair · กลุ่มอื่นนอกจาก medical ตั้งประวัติเป็น `None`

- **set แรกที่เข้าช่องคือชุด test** set ถัดมาในช่องเดียวกันเป็นส่วนเกิน ใช้เป็น dev ได้ · กฎนี้กันการเลือก set หลังอ่านคำตอบ
- ระหว่างเก็บให้กระจาย: `user_ended` ≥ 4 set · มีทั้ง workout แรกของท่าและมีครั้งก่อน · คนทำ 2–3 คน · `hip_sag_or_pike` ทำทั้งสะโพกตกและก้นโด่ง
- ห้ามเปลี่ยน rule logic หรือ similarity model กลางทาง · ถ้าแก้ prompt จากคำตอบที่เห็นบนแอปของ set ไหน ให้ย้าย set นั้นไป dev

**การสร้างคำตอบ (ตัดสิน 2026-11-06):** ไม่ใช้ `sets.llm_feedback` ที่แอปเก็บไว้ แต่สร้างใหม่ทั้งสองฝั่งด้วย `eval/replay_captured.py` จาก input ใน capture หลัง commit เฉลยและ freeze prompt แล้ว

- ฝั่ง RAG ใช้ adapter, retrieval และ `_generate` ของ service ชุดเดียวกับ `POST /feedback` (มี test ยืนยันว่าส่งให้ LLM เหมือนกัน) ฝั่ง no-RAG เปลี่ยนแค่ context
- ความต่างของถ้อยคำระหว่างคำตอบบนแอปกับคำตอบที่สร้างใหม่ไม่ใช่ปัญหา เพราะ eval วัดระบบ ไม่ได้วัดข้อความชิ้นหนึ่ง สิ่งที่ต้องตรงกันคือ prompt, โมเดล, `thinking_level`, KB และ input
- ระหว่างเก็บข้อมูล service ใช้ Groq ฟรีได้ เพราะคำตอบนั้นไม่ถูกนำมาใช้ และ adapter ไม่ส่ง feedback ของ set ก่อนหน้าให้ LLM

**กติกาจูน:** การแก้ข้อบน dev ต้องไม่ดูว่าฝั่งไหนได้คะแนน ดูได้แค่ pass rate รวมและ agreement · หลังรัน test ห้ามแก้แล้วรันใหม่โดยไม่บันทึก (`compare_output/final_log.md`)

**สถิติ**

- **หน่วยวิเคราะห์ = session:** ฝั่งละ 1 sample แล้วลบกันเป็นคู่ · ความแกว่งของ LLM จึงอยู่ในผลต่างของแต่ละ session และสะท้อนอยู่ใน p-value กับ CI แล้ว แต่ทำให้จับความต่างเล็ก ๆ ได้ยากกว่า 3 sample
- **กติกา 1 sample:** ใช้คำตอบแรกที่สร้างสำเร็จ · สร้างใหม่ได้เฉพาะเมื่อ API ล้ม และต้องบันทึก · ห้ามสุ่มใหม่เพราะคำตอบดูไม่ดี
- **ตัวเลขหลัก (1 ตัว):** ผลต่างคะแนนรวม RAG − no-RAG บน 32 session ที่มี fault · Wilcoxon signed-rank + bootstrap 95% CI ระดับ session · รายงาน win/loss ด้วย (sign test ต้องชนะ ≥ 23/32)
- **รายเกณฑ์ 4 ตัว:** ใช้ Holm · **รายข้อ:** สำรวจอย่างเดียว ใช้ BH และห้ามอ้างเป็นผลหลัก
- **A5:** ใช้ McNemar ดูว่าฝั่งไหนไม่ผ่านบ่อยกว่า
- **เกณฑ์ขนาดผล:** ต้องเกิน 5 จุดเปอร์เซ็นต์ (เฉลี่ยได้มากกว่า 1 ข้อจาก 20)

**สรุปได้ว่า "RAG ดีกว่า" เมื่อ:** ผ่านเกณฑ์ขนาดผล, p < 0.05, CI ไม่คร่อม 0 **และ** อัตราไม่ผ่าน A5 ไม่สูงกว่า no-RAG · ถ้าไม่ถึงให้รายงานว่าไม่พบความต่าง ซึ่งก็เป็นผลที่รายงานได้

**ความเชื่อถือของ judge**

- รายงาน % agreement, Fleiss' κ และ **Gwet's AC1** รายข้อ เพราะข้อที่ yes เกือบหมด κ จะต่ำเกินจริง
- ข้อที่ AC1 < 0.6 บน dev ต้องแก้หรือใช้ข้อสำรอง · รายงานผลแยกต่อ judge ด้วย ถ้าข้อสรุปเปลี่ยนเมื่อตัด judge ตัวใดออก ต้องระบุ

**ตัวตรวจว่า eval ใช้ได้จริง**

- **A/A:** สุ่มสร้างคำตอบครั้งที่สอง 8 session (fault เท่านั้น ฝั่งละ 4 ใช้ seed คงที่) แล้วให้ judge ตัดสิน · ค่าเฉลี่ยของผลต่างต้องไม่เกิน 5 จุด และรายงาน SD ว่าคำตอบต่างกันแค่ไหนจาก input เดิม · 8 คู่ใช้เป็นตัวตรวจเท่านั้น ไม่ใช่เกณฑ์ตัดสินผล
- **Sensitivity:** คำตอบกลายพันธุ์ต้องได้คะแนนต่ำกว่าต้นแบบ
- **Convergent:** ผล checklist ต้องไปทางเดียวกับ `judge_pairwise.py` ที่ตัดสินแบบรวม 1 sample ต่อ session

**ข้อจำกัดที่ต้องเขียนในรายงาน:**

- checklist, เฉลย และคำตอบต้นแบบเขียนโดย Claude และผู้เชี่ยวชาญอนุมัติเฉพาะ card กับ `forbidden_advice`
- query ของ RAG สร้างจาก rule card เดียวกับเฉลย คำตอบ RAG จึงอาจตรงกับ card มากกว่าปกติ แผนนี้ลดผลกระทบด้วยการตรวจแค่ "ไม่ขัด" และไม่ให้คะแนนการตอบตรง
- ไม่มีตัวตรวจอิสระบนคำตอบจริง (§4)
- ผู้ออกแบบเคยอ่านคำตอบ dev แล้ว (แก้ด้วย test ใหม่)
- ผลลัพธ์เป็นการประเมินจาก LLM ไม่ใช่ผู้เชี่ยวชาญตัดสินจริง
- set จริงเป็นการตั้งใจทำท่าผิด ไม่ใช่การออกกำลังกายตามปกติ และคำตอบที่ประเมินสร้างใหม่จาก input จริงด้วยระบบเดียวกัน ไม่ใช่ข้อความเดียวกับที่ผู้ใช้เห็น
- ฝั่ง no-RAG ใช้ prompt เดียวกับฝั่ง RAG ซึ่งห้ามอ้างตัวเลขที่ไม่อยู่ใน Context จึงวัดคุณค่าของ KB ภายใต้ prompt นี้ ไม่ได้เทียบกับ LLM ที่ใช้ความรู้ตัวเองได้เต็มที่

## 9. สิ่งที่ต้องตัดสินใจ

1. **ยอมรับขอบเขตของโค้ดใน §4 ไหม:** โค้ดยังเตรียม `facts` ตรวจรูปแบบคำตอบของ judge และคำนวณสถิติ แต่ไม่เปลี่ยนคำตัดสิน
2. **ตัดสินทีละคำตอบ (แนะนำ) หรือเห็นสองคำตอบข้างกัน:** แบบหลังใกล้ "pairwise" เดิมมากกว่า แต่เสียข้อดีใน §4
3. **key ของ DeepInfra:** ต้องสมัครเพิ่ม 1 อัน (ใช้กับ Glimmer และ Mistral Small 3.2)
4. **ผู้เชี่ยวชาญอนุมัติ `forbidden_advice` ได้ไหม:** ถ้าไม่ได้ A5 จะเหลือแค่ตรวจว่าไม่ฝืนเจ็บ ไม่วินิจฉัย และไม่ขัดกับประวัติ ซึ่งอ่อนลง
5. **ท่าไหนใช้อุปกรณ์อะไร:** session ไม่ได้ระบุ แต่ D5 ต้องใช้ · ถ้าไม่มีข้อมูลนี้ D5 จะตรวจได้แค่ว่าไม่สมมติอุปกรณ์ที่ข้อมูลไม่ได้บอก
