# สรุปการทำงานของระบบ RAG Feedback (ฉบับเข้าใจง่าย)

**อัปเดต:** 27 กันยายน 2026 · **สถานะ:** KB v5 + การค้นแบบ R4 + prompt v11 · รอรันการวัดคุณภาพคำตอบ (G1)

---

## 0. ระบบนี้ทำอะไร (1 ย่อหน้า)

ผู้ใช้เล่นท่าออกกำลังกาย 1 เซ็ต (10 ครั้ง) → **ระบบ 1** (ระบบตรวจท่าของอีกทีม) บอกว่า rep ไหนผิด และผิดแบบไหน เช่น "Knee valgus" (เข่าล้มเข้าใน) → **ระบบของเรา (ระบบ 2)** ไปเปิด "ตำรา" ที่เราเตรียมไว้ (งานวิจัยและคู่มือโค้ช) หาข้อมูลเฉพาะอาการนั้น แล้วให้ LLM เขียน feedback เป็นภาษาโค้ชว่า **ผิดอะไร · ทำไมสำคัญ · แก้ยังไง · ครั้งหน้าทำอะไร**

เปรียบง่าย ๆ: **no-RAG** = โค้ชตอบจากความจำ · **RAG** = โค้ชเปิดตำราก่อนตอบ
เป้าหมายของงานทั้งหมดคือพิสูจน์ว่า "เปิดตำรา" ได้คำแนะนำที่ดีกว่า "ตอบจากความจำ"

รองรับ **4 ท่า 10 อาการ**:

| ท่า | อาการที่ระบบ 1 ตรวจได้ |
|---|---|
| Squat | Butt wink (หลังล่างม้วน) · Knee valgus (เข่าล้มเข้า) · Partial squat (ย่อไม่ลึก) |
| Push-up | Hip sag (สะโพกตก) · Partial range of motion (ลงไม่สุด) |
| Lunge | Excessive forward trunk lean (ตัวโน้มหน้า) · Shallow lunge (ย่อไม่ลึก) · Insufficient back knee flexion (เข่าหลังไม่ลง) |
| Bicep curl | Elbow flare (ศอกไหล) · Partial range of motion (ยกไม่สุด) |

## 1. ภาพรวมทั้งระบบ

ระบบแบ่งเป็น 2 ช่วง: **ช่วง A** เตรียมตำรา (ทำครั้งเดียว หรือทำใหม่เมื่อเพิ่มข้อมูล) และ **ช่วง B** ใช้ตำราตอบผู้ใช้ (ทำทุกครั้งที่ผู้ใช้เล่นเสร็จ)

```
ช่วง A: เตรียมตำรา (Knowledge Base, KB)
  A1 รวบรวมแหล่งข้อมูล ──► A2 LLM อ่านแล้วสกัดความรู้ ──► A3 แปลงเป็นเวกเตอร์ เก็บลงฐานข้อมูล
                                                                  │
ช่วง B: ทุก session                                                ▼
  B1 รับผลตรวจท่า ──► B2 แปลงชื่ออาการเป็นคำค้น ──► B3 ค้นตำรา ──► B4 คัดกรอง
                                                                  │
                     B7 บันทึกรายงาน ◄── B6 LLM เขียน feedback ◄── B5 จัดเป็น context
```

**จุดที่วัดผล** (รายละเอียดใน §4):

| ขั้น | คำถามที่วัด | เครื่องมือ |
|---|---|---|
| A1–A3 | ตำรามีของครบและสะอาดไหม | Claude อ่านตรวจ KB, `kb_coverage.py` |
| B2–B5 | ค้นแล้วได้ข้อมูลถูกอาการไหม ได้ครบแค่ไหน | `eval/eval_retrieval.py` (golden set + relevance pool) |
| B6 | คำตอบอ่านง่ายไหม ลอกตำราไหม ดีกว่า no-RAG ไหม | `eval/eval_generation.py`, `eval/judge_pairwise.py` |

## 2. ช่วง A: เตรียมตำรา (Knowledge Base)

### A1 รวบรวมแหล่งข้อมูล
- **ทำอะไร:** เก็บงานวิจัย (PDF) และบทความเว็บ แยกโฟลเดอร์ตามท่า (`data/<ท่า>/`)
- **คัดทิ้ง:** แหล่งที่ไม่น่าเชื่อถือ เช่น grokipedia (วิกิที่ AI เขียน, 84 ชิ้น), ลิงก์ที่ดึงเนื้อหาไม่ได้ (scribd, self.com), งานวิจัยท่า preacher/incline curl ที่สรุปว่า "ยกไม่สุดก็ได้ผลเท่ากัน" (ถ้าปล่อยไว้ LLM อาจบอกผู้ใช้ว่าทำผิดก็ไม่เป็นไร)
- ไฟล์ที่คัดออกเก็บใน `excluded_from_kb/`

### A2 ให้ LLM อ่านแล้วสกัดความรู้ (`data_pipeline/curator.py`)
- **ทำอะไร:** ตัดเอกสารเป็นช่วงละ ~6,000 ตัวอักษร ส่งให้ Gemini (`gemini-3.5-flash`, temperature 0.1) อ่านแล้วกรอก "แบบฟอร์ม":
  - เนื้อหานี้ช่วยแก้ท่าได้ไหม (`is_relevant`) ถ้าไม่ได้ → ทิ้ง
  - แยกประโยคเป็น 4 ประเภท (**kind**):

    | kind | ความหมาย | ตัวอย่าง |
    |---|---|---|
    | `mistake` | ท่าที่ผิด | "เข่าล้มเข้าในตอนย่อ" |
    | `finding` | ผลวิจัย / ตัวเลข | "ก้าวสั้นทำให้แรงที่ข้อต่อสูงขึ้นเกือบ 2 เท่า" |
    | `principle` | หลักการทำให้ถูก | "ศอกงอให้ถึง 90°" |
    | `consequence` | ผลเสียถ้าทำผิด | "เพิ่มแรงกดที่หลังล่าง" |

  - ติด **tag อาการ** ให้แต่ละประโยค (เช่น ประโยคนี้พูดถึง `knee valgus`)
- **ทำไมติด tag รายประโยค (KB v5):** เดิม (v4) ติด tag ทั้งก้อนเอกสาร ประโยคที่ไม่เกี่ยวเลยได้ tag ไปด้วย

### A3 แปลงเป็นเวกเตอร์ เก็บลงฐานข้อมูล (`ingest.py`)
- **ทำอะไร:** 1 ประโยค = 1 ชิ้น (**chunk**) แปลงเป็นเวกเตอร์ด้วย `gemini-embedding-2` แล้วเก็บใน PostgreSQL + pgvector (รันใน Docker) พร้อมป้าย ท่า / kind / tag อาการ / แหล่งที่มา
- **เวกเตอร์คืออะไร:** ตัวเลขชุดหนึ่งที่แทน "ความหมาย" ของประโยค ประโยคที่ความหมายใกล้กันจะมีเวกเตอร์ใกล้กัน ทำให้ค้นด้วยความหมายได้ ไม่ต้องตรงคำ
- **KB ปัจจุบัน:** `kb_gemini_curated_v5` ประมาณ 1,900 ชิ้น

### วัดผลช่วง A

| ตัววัด | ความหมาย | ผลสำคัญ |
|---|---|---|
| การตรวจ KB (`docs/kb_quality_assessment.md`) | จำนวนชิ้นต่ออาการนับอัตโนมัติ ส่วนการตัดสินว่าชิ้นไหนนอกเรื่องหรือใช้ไม่ได้ Claude อ่านแล้วตัดสิน **ยังไม่มีผู้เชี่ยวชาญ (PT) ตรวจ** | เจอว่า push-up ไม่มีข้อมูลอาการของตัวเอง, bicep มีผลวิจัย 199 ชิ้นแต่ใช้กับอาการจริงไม่ได้เลย → หาแหล่งเพิ่มเป็น KB v4 |
| `kb_coverage.py`: จำนวนชิ้นที่ "ใกล้พอ" ต่ออาการ | ค้นด้วยคำค้นนี้แล้วมีข้อมูลในตำรากี่ชิ้น | ใช้เทียบคำค้นดิบกับคำค้นที่ขยาย (ดู B2) · **ข้อควรระวัง:** ตัวเลขนี้หลอกได้ ต้องอ่านเนื้อหาจริงประกอบ |

> คุณภาพของ KB วัดโดยตรงยาก จึงวัดผ่านขั้นค้น (§4.1) เป็นหลัก: ถ้า KB ดีขึ้น การค้นต้องได้ข้อมูลถูกอาการมากขึ้น

## 3. ช่วง B: ทุกครั้งที่ผู้ใช้เล่นเสร็จ

### B1 รับผลตรวจท่าจากระบบ 1
ข้อมูลเป็น JSON: 10 rep, rep ไหนถูก/ผิด, ชื่ออาการ (`error_type`), คะแนน, ผลครั้งก่อน
ตอนนี้ยังไม่ได้ต่อกับระบบ 1 จริง ใช้ข้อมูลจำลอง `mock_data/mock_sessions_per_fault.json` (11 session = 10 อาการ อาการละ 1 session + push-up ที่ไม่มีท่าผิด 1 session)

### B2 แปลงชื่ออาการเป็นคำค้น (`error_taxonomy.py`)
- **ทำอะไร:** เปลี่ยนชื่อสั้น ๆ เป็นประโยคบรรยายอาการ
  `Butt wink` → *"Lumbar flexion (butt wink): posterior pelvic tilt and rounding of the lower back at the bottom of the squat"*
- **ทำไมต้องแปลง:** ค้นด้วยชื่อดิบแล้วบางอาการหาไม่เจอเลย หรือแย่กว่านั้นคือ **เจอแต่ผิด**

  | อาการ | ค้นด้วยชื่อดิบ | ค้นด้วยคำที่ขยายแล้ว |
  |---|---|---|
  | Butt wink | 0 ชิ้น | 13 ชิ้น |
  | Elbow flare | 0 ชิ้น | 9 ชิ้น |
  | Partial squat | 21 ชิ้น แต่ผิดหมด | 1 ชิ้น ตรง |

- **คำค้นเขียนยังไง:** Claude เขียนเองโดยเลียนคำที่ KB ใช้ รูปแบบคือ "ชื่ออาการ + หลายสำนวนของ KB รวมในประโยคเดียว" เช่น *"flare outward **or** drift away"* ไม่มีคำค้นไหนตรงกับประโยคใน KB เป๊ะ (คำซ้ำกับประโยค KB ที่ใกล้สุด 25–71%) แต่ถือว่า **จูนเข้าหา KB** ซึ่งมีความเสี่ยงเรื่อง bias ดู §7.1
- วิธีนี้เรียกว่า **query expansion** (ขยายคำค้น) หรือ **controlled vocabulary mapping** (แปลงชื่อเป็นศัพท์มาตรฐาน) เป็นวิธีมาตรฐานเมื่อชื่อที่ผู้ใช้ส่งมาไม่ตรงกับภาษาของเอกสาร

### B3 ค้นตำรา (`test_rag_compare.py`)
- **ปัจจุบันใช้แบบ R4:** ต่อ 1 อาการ สร้างคำค้น **3 มุม** (`QUERY_PROFILE`)

  | มุม | คำค้นจริง | ตั้งใจให้เจอ |
  |---|---|---|
  | *what* ผิดยังไง | คำค้นเดิมจาก B2 เช่น *"Knee valgus: knees caving inward…"* | ชิ้น `mistake` |
  | *why* ทำไมสำคัญ | *"Harmful consequences, injury risk and joint stress caused by: "* + คำค้นเดิม | ชิ้น `consequence` / `finding` |
  | *fix* แก้ยังไง | *"How to correct it, coaching cues and corrective exercises for: "* + คำค้นเดิม | ชิ้น `principle` และวิธีแก้ |

- **ขั้นตอน:**
  1. คำค้นแต่ละอันค้นใน 4 kind ได้ผู้สมัคร kind ละ 12 ชิ้น กรองเฉพาะท่าเดียวกัน + ชิ้นที่มี tag อาการนั้น (ถ้ามี)
  2. คัดด้วยระยะ **โดยเทียบกับชิ้นที่ดีที่สุดของคำค้นนั้นเอง** (ไม่ใช่ของคำค้นรวม)
  3. รวมผลทั้ง 3 คำค้น ตัดซ้ำ แล้วแบ่งตามโควตาใน B4
- **ทำไมต้องทำ:** คำค้นเดิมเขียนเหมือนประโยค "ท่าผิด" ชิ้น `mistake` จึงใกล้ที่สุดเสมอ ชิ้นที่ตอบคำถามอื่น (ผลเสีย, วิธีแก้) อยู่ไกลกว่าจึงหลุดเกณฑ์ พอมีคำค้นที่ถามเรื่องนั้นตรง ๆ ก็ได้ข้อมูลแนว "สาเหตุ → วิธีแก้" เพิ่ม เช่น "กล้ามเนื้อต้นขาด้านในตึงทำให้เข่าล้มเข้า"
- ประโยคนำหน้าของ why/fix เป็นประโยคกลาง ใช้เหมือนกันทุกอาการ และตั้งไว้ก่อนรันผล ไม่ได้จูนจากผลวัด · เทคนิคนี้เรียกว่า **multi-query retrieval** หรือ **query decomposition**

### B4 คัดกรอง (gate)
ค้นมาได้หลายชิ้น แต่ไม่ได้ส่งให้ LLM ทั้งหมด ต้องผ่าน 3 ด่าน:
1. **ใกล้พอ:** ต้องใกล้เกือบเท่าชิ้นที่ดีที่สุด (ห่างจากอันดับ 1 ไม่เกิน 0.03)
2. **ไม่ซ้ำ:** ประโยคที่คำซ้ำกันเกิน 72% ถือว่าซ้ำ เก็บไว้ชิ้นเดียว
3. **โควตาต่อ kind:** `mistake` 3 · `finding` 2 · `principle` 2 · `consequence` 2 = **สูงสุด 9 ชิ้นต่ออาการ**

### B5 จัดเป็น context
แต่ละชิ้นมีหัวบอกประเภท อาการ และแหล่ง แล้วตามด้วยประโยค เช่น
`[finding | re: Knee valgus | source: TheBackSquat]` + ประโยค

ถ้า session ไม่มีท่าผิด → ค้น "หลักการทำท่าที่ถูก" แทน

### B6 LLM เขียน feedback
- **โมเดล:** `gemini-3.5-flash-lite` · temperature 0.7 (คงไว้ทุกรอบเพื่อเทียบข้ามรอบได้)
- **prompt v11** สั่งให้เขียนแบบโค้ชในยิม:
  - ความคืบหน้าเทียบครั้งก่อน
  - ต่ออาการ: คืออะไร · ทำไมสำคัญ · วิธีแก้ 4 แบบ (คำนึกระหว่างทำ, ปรับ setup, ท่าฝึกแก้, วิธีเช็กตัวเอง) · rep ไหนที่ผิด
  - แผนครั้งหน้า 2–3 ข้อ
- **กฎสำคัญ:** ห้ามแต่งตัวเลขหรือแหล่งที่ไม่มีใน context · ต้อง "แปล" ศัพท์เทคนิคเป็นภาษาคนทั่วไป ห้ามลอกประโยคจากงานวิจัย · ตัวอย่างใน prompt ต้องเป็นเรื่องนอกงานจริง (ข้อมือ, คอ, เวลาพัก) ไม่อย่างนั้น LLM จะลอกตัวอย่างไปตอบ

**การแปลศัพท์ทำยังไง:** เราไม่ได้ให้พจนานุกรมกับ LLM เพราะ LLM รู้กายวิภาคอยู่แล้วจากข้อมูลที่ใช้ฝึก เราแค่สั่งผ่าน prompt ("Translation rule")
- ทุกครั้งที่ใช้ศัพท์กายวิภาค/ชีวกลศาสตร์ ต้องอธิบายความหมายในประโยคเดียวกัน หรือใช้คำง่ายแทนไปเลย
- มีรายชื่อศัพท์ที่ต้องแปล และรายชื่อศัพท์ที่ใช้ได้โดยไม่ต้องอธิบาย (เช่น rep, set)
- ตัวอย่าง: *hip extensors and ankle plantar flexors* → *hips and calves* · *knee extensors* → *quads* · *biarticular* → *cross both your elbow and your shoulder*
- การตรวจว่าแปล **ถูก** ยังไม่มีอย่างเป็นระบบ ดู §7.3

**temperature คืออะไร:** ระดับความสุ่มตอนที่ LLM เลือกคำถัดไป
- **0:** เลือกคำที่น่าจะเป็นที่สุดเกือบทุกครั้ง ถามซ้ำได้คำตอบแทบเหมือนเดิม
- **สูง (0.7–1):** ภาษาหลากหลายและเป็นธรรมชาติขึ้น แต่ถามซ้ำได้คำตอบไม่เหมือนเดิม และมีโอกาสหลุดจากข้อมูลที่ให้ไปสูงขึ้นเล็กน้อย

| ใช้ทำอะไร | temperature | เหตุผล |
|---|---|---|
| สกัดความรู้ (A2) | 0.1 | อยากให้ผลสม่ำเสมอ |
| LLM ผู้ตัดสิน (§4.2) | 0 | ตัดสินคู่เดิมต้องได้ผลเดิม |
| **เขียน feedback (B6)** | **0.7** | ภาษาโค้ชเป็นธรรมชาติ คงไว้ทุกรอบเพื่อเทียบข้ามรอบได้ |

ผลต่อการทดลอง: รัน session เดิม 2 ครั้งได้คำตอบต่างกัน **รันครั้งเดียวจึงสรุปไม่ได้** G1 เลยสร้างคำตอบ 5 ครั้งต่อ session แล้วใช้สถิติ ส่วนการค้นไม่ได้รับผลจาก temperature (embedding ให้ผลเดิมทุกครั้ง) จึงวัดการค้นซ้ำได้ทุกขั้น

### B7 บันทึกรายงาน
เก็บใน `compare_output/*.md` (+ `.json`): ค่าที่ตั้ง, ตัวเลขการค้น, context ที่ส่งจริง, คำตอบ RAG และ no-RAG วางคู่กัน

## 4. การวัดผล: วัดอะไร อ่านยังไง

### 4.1 วัดการค้น (ขั้น B2–B5) ด้วย `eval/eval_retrieval.py`

มีไม้บรรทัด 2 อัน:

**(ก) Golden set** (`eval/golden_chunks.json`): ชุดเฉลยที่ระบุว่าแต่ละอาการ "ควรได้" ข้อมูลแบบไหน และ "ห้ามได้" แบบไหน

**วิธีสร้าง** (11 ก.ย., บน KB v4):
1. ค้นด้วยคำค้นจาก B2 ทีละ (อาการ × kind) เอา 14 อันดับแรก
2. Claude อ่านทีละชิ้นแล้วติดป้าย:
   - ตรงอาการ → ใส่ `must_hit` (เก็บเป็นข้อความบางส่วนของชิ้น เช่น "Lumbar flexion (butt wink)")
   - เป็นของอาการอื่นแต่ระบบดึงเข้ามาจริงหรือเกือบเข้า หรือเป็นหลักการที่จะทำให้ท่าผิดหนักขึ้น → ใส่ `must_not_hit`
   - ที่เหลือไม่ใส่ ถือเป็นกลาง (neutral)
3. ตอนเปลี่ยนเป็น KB v5 เพิ่มสำนวนใหม่เข้าไปโดยไม่ลบของเดิม (รอบแรกได้ 4/10 ซึ่งผิด เพราะ KB พูดถูกแต่ใช้คำต่าง)

**วิธีให้คะแนน:** ชิ้นที่เข้า context มีข้อความตรง `must_hit` = good · ตรง `must_not_hit` = bad · นอกนั้น = neutral · จุดอ่อนของวิธีนี้ดู §7.2

| ตัววัด | ความหมาย | ยิ่ง…ยิ่งดี |
|---|---|---|
| **hit** | กี่อาการ (จาก 10) ที่ได้ข้อมูลตรงอาการอย่างน้อย 1 ชิ้น | สูง |
| **precision** | สัดส่วนชิ้นที่ "ตรงเฉลย" ในสิ่งที่ส่งให้ LLM | สูง |
| **bad** | จำนวนชิ้นที่ผิดชัด ๆ หรือเป็นอันตราย (เช่น "ยกไม่สุดก็ได้ผลเท่ากัน") | ต่ำ (สำคัญที่สุด เพราะคือต้นเหตุของคำแนะนำผิด) |

**(ข) Relevance pool** (`eval/relevance_pool.json`): ให้ LLM อีกตัว (`gemini-3.8-flash`) ตรวจข้อมูลในตำราว่าชิ้นไหนเกี่ยวกับอาการไหน ได้ข้อมูลที่เกี่ยวข้องจริง **411 ชิ้น** ใช้เป็นตัวหาร

| ตัววัด | ความหมาย | ยิ่ง…ยิ่งดี |
|---|---|---|
| **recall** | ดึงข้อมูลที่เกี่ยวข้องได้กี่ชิ้นจาก 411 (micro = รวมทุกอาการ, macro = เฉลี่ยต่ออาการ) | สูง |
| **ceiling** | เพดานของ recall: ส่งได้แค่อาการละ 9 ชิ้น ต่อให้ค้นสมบูรณ์แบบก็ได้สูงสุด ~21% | ใช้อ่านประกอบ |
| **wrong_fault** | ชิ้นที่เป็นของอาการอื่นแต่ถูกดึงมา | ต่ำ |
| **pool-precision** | สัดส่วนชิ้นใน context ที่เกี่ยวข้องจริง | สูง |
| **miss by reason** | ชิ้นที่ควรได้แต่หลุด หลุดเพราะอะไร: tag สะกดผิด / ไม่ติดอันดับ / ห่างเกิน / โควตาเต็ม / ซ้ำ | ใช้หาจุดที่ต้องแก้ |

**กติกาเก็บการเปลี่ยนแปลงฝั่งการค้น** (ต้องผ่านทุกข้อ): recall ขึ้น · wrong_fault ไม่เพิ่ม · bad ไม่เพิ่ม · pool-precision ไม่ตกเกิน 0.05

### 4.2 วัดคำตอบ (ขั้น B6)

**(ก) `eval/eval_generation.py`**: ตัวเลขอัตโนมัติ ไม่ต้องใช้ LLM

| ตัววัด | ความหมาย | ยิ่ง…ยิ่งดี |
|---|---|---|
| **unglossed jargon** | ศัพท์เทคนิคที่ใช้โดยไม่อธิบาย (เทียบกับรายการใน `eval/jargon_terms.json`) นับว่า "อธิบายแล้ว" ถ้าภายใน 120 ตัวอักษรหลังศัพท์มีวงเล็บ หรือคำอย่าง "means", "which is" · **เช็กแค่ว่ามีคำอธิบาย ไม่ได้เช็กว่าอธิบายถูก** | ต่ำ |
| **longest shared n-gram** | ประโยคที่ลอกจาก context ยาวสุดกี่คำติดกัน (no-RAG ได้ ~6 คำจากความบังเอิญ ใช้เป็นเส้นฐาน) | ต่ำ (ใกล้เส้นฐาน) |

**(ข) `eval/judge_pairwise.py`**: ให้ LLM ผู้ตัดสินเทียบคำตอบ 2 แบบ **โดยไม่บอกว่าอันไหนมาจากไหน** (สลับซ้าย/ขวาแบบสุ่ม)

| ตัววัด | ความหมาย |
|---|---|
| **win rate 4 ด้าน + overall** | เกณฑ์ตามงานวิจัย SportsGPT: ความถูกต้อง (Accuracy) · ความครบถ้วนและลึก (Comprehensiveness) · ความเฉพาะแบบผู้เชี่ยวชาญ (Professionalism) · นำไปทำได้จริง (Feasibility) |
| **sign test (p < 0.05)** | ชนะแบบไม่ใช่ความบังเอิญไหม |
| **control** | session ที่ context เหมือนกันทั้งสองฝั่ง ควรออก ~50:50 ถ้าไม่ใช่ แปลว่าผู้ตัดสินลำเอียง |
| **position check** | ผู้ตัดสินชอบเลือกฝั่งซ้ายหรือขวาเป็นพิเศษไหม ควรใกล้ 50% |
| **reference none / union** | รัน 2 แบบ: ผู้ตัดสินไม่เห็นตำรา กับเห็นตำรา (เพราะผู้ตัดสินที่ไม่เห็นตำรามักลงโทษข้อมูลเฉพาะจากงานวิจัยที่ "ดูแปลก") |

**(ค) อ่านเทียบ (โดย Claude)**: อ่านคำตอบ RAG กับ no-RAG คู่กัน หาประโยคที่ผิด หรือใช้ข้อมูลผิดเงื่อนไข (ใช้เล่าเป็นตัวอย่าง แต่สรุปเป็นสถิติไม่ได้ เพราะ temperature 0.7 ทำให้คำตอบสุ่มต่างกันทุกครั้ง)

## 6. สถานะตอนนี้

### สิ่งที่รู้แล้ว
- **ตำรา (KB v5) และการค้น (R4) ดีขึ้นชัดเจน** ได้ข้อมูลตรงอาการครบ 10/10 และไม่มีข้อมูลผิดชัด ๆ ใน context
- **คำตอบอ่านง่ายขึ้น** ศัพท์ที่ไม่อธิบายเกือบเป็นศูนย์ และไม่ลอกงานวิจัยแล้ว
- **RAG ชนะเมื่อตำราให้ "สาเหตุ → วิธีแก้" และ "ตัวเลขที่เช็กได้"** เช่น Butt wink: no-RAG ให้ลดความลึก ส่วน RAG ให้ยืนกว้างขึ้นและเข่าบานออก ซึ่งแก้ที่ต้นเหตุ
- **ต้นเหตุที่ RAG ยังไม่ชนะชัด:** ตำรามีแต่สิ่งที่ LLM รู้อยู่แล้ว (นิยามอาการ ผลวิจัยทั่วไป) แต่ขาด **ท่าฝึกแก้ ปริมาณการฝึก (dose) และสาเหตุ → วิธีแก้**

### สิ่งที่ยังไม่รู้
- **ยังไม่มีหลักฐานเชิงสถิติว่าคำตอบดีขึ้น** ตัวเลขทั้งหมดในข้อ 5 เป็นการวัดการค้น ส่วนการวัดคำตอบ (G1) เครื่องมือพร้อมแล้วแต่ยังไม่ได้รันเต็ม
- **LLM เอาผลวิจัยไปใช้ผิดเงื่อนไข** 3 เคสในรอบ v13 เช่น ผลการทดสอบ "วางแผ่นรองส้น 2 นิ้ว" ถูกแปลงเป็นคำแนะนำให้ทำทุกเซ็ต, แรงกดหลัง 1,838 N ของท่าปกติถูกอ้างเป็นผลของสะโพกตก

### ขั้นต่อไป (เรียงตามลำดับ)

| ลำดับ | งาน | ตัววัดที่จะใช้ |
|---|---|---|
| 1 | **G1:** รันวัดคุณภาพคำตอบ R0 เทียบ R4 (5 คำตอบต่อ session, ผู้ตัดสิน 2 แบบ) | win rate + sign test, control, position check |
| 2 | **ขั้น P (prompt):** บังคับให้ผลวิจัยคงเงื่อนไขเดิม, ต้องใช้ข้อมูลเฉพาะจากตำราอย่างน้อย 1 ข้อต่ออาการ, ปริมาณการฝึกต้องมาจากตำรา | pairwise judge + `eval_generation.py` |
| 3 | **ขั้น K (ตำรา):** เพิ่มเนื้อหาปริมาณการฝึก (ACSM, NSCA), ท่าฝึกแก้ต่ออาการ, การทดสอบหาสาเหตุ | สร้าง relevance pool ใหม่ → วัดการค้น → วัดคำตอบ |
| 4 | หาแหล่งวิธีแก้ elbow flare แทน grokipedia | golden set (bad ของ elbow flare) |
| 5 | R6 reranker เมื่อมีเครื่องที่แรงกว่า | เกณฑ์เดียวกับ R0–R5 |

งานเช็ก bias จาก §7 (ทำคู่ขนานได้ ไม่ต้องรอข้อบน):

| งาน | แก้ข้อจำกัดข้อไหน |
|---|---|
| ขอ `form_rules.py` จากทีมระบบ 1 หรือให้ PT ยืนยันว่าคำค้นทั้ง 10 ข้อตรงกับกฎจริง | §7.1 ข้อ ค |
| ทดสอบคำค้นแบบปิดตา (ให้ LLM เขียนคำค้นจากชื่อกฎโดยไม่เห็น KB แล้วเทียบ recall) | §7.1 ข้อ ข |
| ให้ PT ตรวจคู่ "ศัพท์ → คำแปล" ที่ LLM ใช้ | §7.3 |

## 7. ข้อจำกัดและความเสี่ยงเรื่อง bias

### 7.1 คำค้นถูกจูนเข้าหา KB (B2)
คำค้นเขียนโดยเปิดดู KB ไปด้วย (ดู B2) ต้องแยกความเสี่ยงเป็น 3 เรื่อง เพราะหนักไม่เท่ากัน

| เรื่อง | ควรกังวลไหม | เหตุผล |
|---|---|---|
| **ก. จูนคำค้นให้ใช้ภาษาเดียวกับตำรา** | น้อย | เป็นวิธีปกติ เป้าของการค้นคือหาของที่เกี่ยวข้อง ถ้าคำค้นยังหมายถึงอาการเดียวกัน การใช้คำเดียวกับตำราไม่ทำให้ผลผิด |
| **ข. ตัวเลขวัดผลสวยเกินจริง** | **ควรกังวล** | golden set สร้างจากผลที่คำค้นชุดเดียวกันค้นมา และคนจูนกับคนให้คะแนนเป็นฝ่ายเดียวกัน ตัวเลขจึงบอกได้แค่ว่า "คำค้นเข้ากับ KB" ไม่ได้บอกว่า "คำค้นตรงกับอาการจริง" · มีเคสที่จูนจากผลวัด (คำค้น bicep partial ROM ถูกเขียนใหม่หลังเห็นผล) และไม่มีชุดข้อมูลแยกไว้ทดสอบ ตัวเลข 10/10 จึงเป็นค่าที่มองโลกในแง่ดี |
| **ค. ตีความอาการผิดตั้งแต่ต้น** | **กังวลมากที่สุด** | กฎของระบบ 1 ชื่อ "เข่าไม่เลยปลายเท้า" (เข่าเลื่อนไปข้างหน้า) แต่คำค้นเขียนว่า "knees caving inward" (เข่าล้มเข้าใน) ซึ่งเป็นคนละอาการ ถ้าเป็นแบบนั้นจริง การจูนยิ่งทำให้ดึงข้อมูลผิดอาการได้แม่นขึ้น และตัวเลขวัดผลจะไม่จับได้ · ยังค้างอยู่ รอ `form_rules.py` |

**วิธีทั่วไปที่ใช้แก้ปัญหาค้นศัพท์เฉพาะ เทียบกับที่เราทำ:**

| วิธี | เราทำไหม |
|---|---|
| ขยายคำค้นจากพจนานุกรม/ontology กลาง (สายการแพทย์ใช้ MeSH, UMLS) | ทำแบบเขียนเอง (`error_taxonomy.py`) |
| ให้ LLM เขียนคำค้นใหม่ หรือแต่งคำตอบสมมติแล้วใช้ค้น (multi-query, HyDE) | ใช้ multi-query (R4) |
| ค้นด้วยคีย์เวิร์ดร่วม (hybrid BM25) | ลองแล้ว (R5) ไม่ผ่าน |
| กรองด้วย tag/metadata | ทำ (tag อาการ) |
| reranker | เขียนโค้ดแล้ว เลื่อนไว้ (R6) |

**จุดที่ต่างจากวิธีมาตรฐาน:** ปกติคำขยายมาจากแหล่งที่ไม่ขึ้นกับตำรา (ontology, ผู้เชี่ยวชาญ, หรือ LLM ที่ไม่เห็นตำรา) ของเราเขียนโดยเปิดดู KB ซึ่งใกล้กับการ "จูนบนข้อสอบ" · ทางแก้อยู่ในตารางงานเช็ก bias ท้าย §6 และหลังจากนี้ต้องไม่จูนคำค้นจากผลวัดอีก

### 7.2 Golden set
- **วนกลับเข้าหาตัวเอง:** ผู้สมัครมาจาก 14 อันดับแรกของคำค้นเดียวกับที่ถูกวัด ชิ้นดีที่คำค้นนี้ไม่เคยเจอจึงไม่มีทางอยู่ในเฉลย และวัด recall ไม่ได้ · นี่คือเหตุผลที่สร้าง **relevance pool** ภายหลัง (ผู้สมัครจาก tag + 40 อันดับแรกของหลายคำค้น ติดป้ายโดย LLM อีกตัว) ซึ่งใกล้กับวิธีมาตรฐานด้าน IR ที่เรียกว่า **pooling** (แบบ TREC) มากกว่า
- **จับคู่ด้วยข้อความเป๊ะ ๆ:** พอ KB ใช้คำเปลี่ยน ตัวเลขก็เพี้ยน เช่น precision ของ R4 ตก 0.61 → 0.48 ทั้งที่ context ไม่ได้แย่ลง
- **ไม่มีผู้เชี่ยวชาญตรวจ:** Claude ติดป้ายคนเดียว · วิธีมาตรฐานคือให้ผู้ติดป้ายอย่างน้อย 2 คนติดแยกกัน แล้ววัดว่าเห็นตรงกันแค่ไหน (inter-annotator agreement) ถ้าใช้ LLM ติดป้าย (เช่น relevance pool) ก็ควรสุ่มส่วนหนึ่งให้คนตรวจเทียบ

### 7.3 การแปลศัพท์
- ตัววัด unglossed jargon เช็กแค่ว่ามีคำอธิบาย ถ้า LLM แปลผิด ตัวเลขนี้ก็ยังนับว่าผ่าน
- ที่ตรวจความถูกจริงคือ Claude อ่านตัวอย่างไม่กี่ข้อ (ถูกทั้งหมด) แต่ไม่ใช่การตรวจทั้งหมด · เกณฑ์ Accuracy ใน G1 ช่วยได้บางส่วน แต่ผู้ตัดสินเป็น LLM ตระกูลเดียวกัน
- **ทางแก้:** ดึงคู่ "ศัพท์ → คำแปล" ทั้งหมดจากคำตอบ (น่าจะไม่กี่สิบคู่) ให้ PT ติ๊กถูก/ผิด

### 7.4 อื่น ๆ
- **KB ยังไม่มีผู้เชี่ยวชาญตรวจ:** การตัดสินว่าแหล่งไหนนอกเรื่องหรือไม่น่าเชื่อถือ Claude เป็นคนอ่านตัดสิน (ผู้ใช้อนุมัติการถอดแหล่ง) ห้ามเขียนในรายงานว่า "ผู้เชี่ยวชาญตรวจแล้ว"
- **temperature 0.7:** ผลของ generation ต้องดูจากหลายรอบเสมอ ตัวอย่างจากรันเดียวใช้เล่าได้ แต่สรุปเป็นผลไม่ได้
- **ผู้ตัดสินเป็น LLM ตระกูลเดียวกับตัวสร้างคำตอบ (Gemini):** เพราะมี API key แค่ของ Gemini จึงใช้คนละรุ่นแทน
- **B0 สร้างซ้ำไม่ได้แล้ว** เพราะ R0 แก้ข้อมูลใน DB ไป จุดเทียบที่เก่าที่สุดที่ยังรันได้คือ R0

## ภาคผนวก: คำศัพท์

| คำ | ความหมายแบบง่าย |
|---|---|
| RAG | ให้ LLM ค้นตำราก่อนตอบ (Retrieval-Augmented Generation) |
| KB | Knowledge Base = ตำราที่เราเตรียมไว้ |
| chunk | ข้อมูล 1 ชิ้นในตำรา (ส่วนใหญ่คือ 1 ประโยค) |
| kind | ประเภทของชิ้นข้อมูล: mistake / finding / principle / consequence |
| tag อาการ | ป้ายบอกว่าประโยคนี้พูดถึงอาการไหน |
| embedding / เวกเตอร์ | ตัวเลขแทนความหมายของประโยค ใช้ค้นด้วยความหมาย |
| context | ชิ้นข้อมูลที่คัดแล้วส่งให้ LLM (อาการละไม่เกิน 9 ชิ้น) |
| gate | ด่านคัดกรองว่าชิ้นไหนได้เข้า context |
| golden set | ชุดเฉลยว่าอาการไหนควรได้/ห้ามได้ข้อมูลแบบไหน (Claude ติดป้าย) |
| query expansion | ขยายชื่อสั้น ๆ ให้เป็นคำค้นที่ใช้ภาษาเดียวกับเอกสาร |
| multi-query | ค้นหลายคำค้นต่อ 1 คำถาม แล้วรวมผล (R4 = what / why / fix) |
| relevance pool | ชุดข้อมูลที่ LLM ตรวจแล้วว่าเกี่ยวกับอาการไหน (411 ชิ้น) |
| recall | ดึงของที่ควรได้มาได้กี่ส่วน |
| precision | ของที่ดึงมาถูกกี่ส่วน |
| ablation | ทดลองเปลี่ยนทีละอย่าง เพื่อดูว่าแต่ละอย่างมีผลแค่ไหน |
| temperature | ความสุ่มของ LLM (0.7 = ตอบไม่เหมือนเดิมทุกครั้ง) |
