## ภาพรวม 5 ขั้น

ระบบแบ่งเป็น 2 ช่วง:
- **ช่วงเตรียมตำรา (ขั้น 1–3):** ทำครั้งเดียว หรือทำใหม่เมื่อเพิ่มหรือแก้ข้อมูล
- **ช่วงใช้งาน (ขั้น 4–5):** ทำทุกครั้งที่ผู้ใช้เล่นจบ 1 เซ็ต

```
ช่วงเตรียมตำรา (Knowledge Base)
  ┌────────────────────┐   ┌──────────────────────────┐   ┌──────────────────────┐
  │ 1. รวบรวมแหล่งข้อมูล │──►│ 2. คัดกรองและสกัดความรู้     │──►│ 3. Ingest             │
  │    PDF + เว็บ        │   │    ด้วย LLM (curator)     │   │    embed → pgvector   │
  └────────────────────┘   └──────────────────────────┘   └──────────┬───────────┘
                                                                     │ KB v5 (1,897 ชิ้น)
ช่วงใช้งาน (ทุก session)                                                ▼
  ผลตรวจท่าจากระบบ 1 ──► ┌──────────────────────────────────────┐   ┌──────────────────────┐
  (JSON 10 rep)        │ 4. ค้นคืนและคัดเลือกบริบท                  │──►│ 5. สร้างคำแนะนำด้วย LLM │──► feedback
                       │ 4.1 รับผลตรวจท่า  4.2 แปลงอาการเป็นคำค้น  │   │    prompt v11          │   + รายงาน
                       │ 4.3 ค้นหลายมุม    4.4 คัดกรอง  4.5 จัด context │   └──────────────────────┘
                       └──────────────────────────────────────┘
```

**ชื่อที่ใช้ในเอกสารนี้**

| ขั้น | ชื่อไทย | ชื่ออังกฤษ | ไฟล์หลัก |
|---|---|---|---|
| 1 | รวบรวมแหล่งข้อมูล | Data Collection | `data/<ท่า>/`, `excluded_from_kb/` |
| 2 | คัดกรองและสกัดความรู้ด้วย LLM | LLM Curation & Knowledge Extraction | `data_pipeline/curator.py` |
| 3 | Ingest เข้าฐานข้อมูลเวกเตอร์ | Embedding & Indexing | `ingest.py`, `embedding_config.py` |

| 5 | สร้างคำแนะนำด้วย LLM | Feedback Generation | `test_rag_compare.py` (prompt v11) |

**ขั้นย่อยของขั้น 4**

| ขั้นย่อย | ชื่อไทย | ชื่ออังกฤษ | ทำอะไร |
|---|---|---|---|
| 4.1 | รับผลตรวจท่า | Input Parsing | อ่าน JSON จากระบบ 1: rep ไหนผิด ผิดแบบไหน |
| 4.2 | แปลงชื่ออาการเป็นคำค้น | Query Expansion | `Butt wink` → ประโยคบรรยายอาการที่ใช้ภาษาเดียวกับ KB |

| 4.4 | คัดกรองผลค้น | Filtering (Gating) | ตัดชิ้นที่ไกลเกิน ตัดชิ้นซ้ำ และจำกัดโควตาต่อ kind |
| 4.5 | จัดรูป context | Context Assembly | ใส่หัวบอกประเภท อาการ และแหล่งให้แต่ละชิ้น |

## ขั้น 1: รวบรวมแหล่งข้อมูล (Data Collection)

### 1.1 เป้าหมาย
หาเอกสารที่ตอบคำถาม **"ท่าผิดแบบนี้ เกิดอะไรขึ้น และแก้ยังไง"** สำหรับแต่ละอาการ ไม่ใช่เอกสารเกี่ยวกับท่านั้นทั่ว ๆ ไป

### 1.2 ขั้นตอน
1. **หาแหล่ง** 2 ประเภท:
   - งานวิจัย (PDF) เช่น biomechanics, EMG, การบาดเจ็บ
   - หน้าเว็บของโค้ชหรือองค์กรรับรองผู้ฝึกสอน (NASM, ACE) ใส่ลิงก์ไว้ใน `urls.txt`
2. **แยกโฟลเดอร์ตามท่า:** `data/squat/`, `data/lunge/`, `data/push-up/`, `data/bicep-curl/` (ชื่อโฟลเดอร์ใช้เป็นป้าย "ท่า" ของทุกชิ้นในขั้น 3)
3. **ดึงเนื้อหาเว็บ:** ใช้ `trafilatura` ดึงเฉพาะเนื้อหาหลัก ไม่เอาเมนูหรือ sidebar · ลิงก์ที่ตายแล้วใช้ snapshot จาก Wayback Machine แทน
4. **คัดทิ้ง** (คนตัดสิน: Claude อ่านแล้วเสนอ ผู้ใช้อนุมัติ) ย้ายไป `excluded_from_kb/`

### 1.3 ผลการทดสอบ

### 1.4 ข้อจำกัดและงานค้าง
- **ยังขาดข้อมูลเชิงปฏิบัติ:** ท่าฝึกแก้ (corrective drill), ปริมาณการฝึก (dose เช่น กี่เซ็ต กี่ครั้ง) และความสัมพันธ์ "สาเหตุ → วิธีแก้" นี่คือต้นเหตุหลักที่ RAG ยังไม่ชนะ no-RAG ชัดเจน (ดูขั้น 5)
- **วิธีแก้ elbow flare ยังไม่มีแหล่งทดแทน** หลังถอด grokipedia
- **ยังไม่มีผู้เชี่ยวชาญ (PT) ตรวจแหล่ง** การตัดสินว่าแหล่งไหนนอกเรื่องหรือไม่น่าเชื่อถือ Claude เป็นคนอ่าน
- **แหล่งใหม่ 22 ไฟล์ยังไม่เข้า KB:** `data/` มี PDF ที่เพิ่มเมื่อ 25–27 ก.ย. สำหรับ KB v6 (เช่น `Papadakis2024_BackSquatErrors…`, `Lu2022_HeelLiftInsoles…`) ยังไม่ได้ผ่านขั้น 2

## ขั้น 2: คัดกรองและสกัดความรู้ด้วย LLM (LLM Curation & Knowledge Extraction)

### 2.1 เป้าหมาย
เปลี่ยนเอกสารยาว ๆ ให้เป็น **ประโยคความรู้สั้น ๆ ที่มีป้ายกำกับ** เพื่อให้ขั้น 4 ค้นเจอแม่นขึ้น และทิ้งส่วนที่ไม่เกี่ยวกับการแก้ท่า

### 2.2 ขั้นตอน (`data_pipeline/curator.py`)
1. **ตัดเอกสารเป็นช่วง (window)** ช่วงละ 6,000 ตัวอักษร ซ้อนกัน 300 ตัวอักษร
2. **ส่งแต่ละช่วงให้ LLM:** `gemini-3.5-flash` ที่ temperature 0.1 (ต้องการผลสม่ำเสมอ) กรอกแบบฟอร์มที่กำหนดโครงสร้างไว้:

   | ช่อง | ความหมาย |
   |---|---|
   | `is_relevant` | ช่วงนี้ช่วยแก้ท่าได้ไหม ถ้าไม่ได้ → ทิ้งทั้งช่วง (นิยามแคบ: ต้องเกี่ยวกับฟอร์ม ข้อผิดพลาด หรือการบาดเจ็บของท่านี้ ไม่ใช่ sports science ทั่วไป) |
   | `exercise_type` | เอกสารนี้พูดถึงท่าอะไร ใช้ตรวจว่าตรงกับโฟลเดอร์ไหม |
   | 4 kind | แยกประโยคเป็น `mistake` (ท่าที่ผิด) · `finding` (ผลวิจัยหรือตัวเลข) · `principle` (หลักการทำให้ถูก) · `consequence` (ผลเสียถ้าทำผิด) |
   | `applies_to_fault` | tag อาการ **รายประโยค** ว่าประโยคนี้พูดถึงอาการไหน (ว่างได้ถ้าเป็นความรู้ทั่วไป) |

3. **กฎพิเศษใน prompt ของ curator** (เพิ่มหลังเจอปัญหา):
   - ห้ามติด tag ให้ประโยคที่บอกว่าทำผิดแล้วได้ผลเท่ากัน (เช่น "partial ROM ให้ผลเท่า full ROM")
   - ห้ามติด tag ให้ประโยคที่เจาะจงท่าแปรผัน (preacher, incline, cable curl) ซึ่งใช้กับท่ามาตรฐานไม่ได้
4. **ทำความสะอาดอัตโนมัติ:** `normalize_ocr_degrees()` แก้ OCR ที่อ่านสัญลักษณ์องศาเป็นเลข 8 ("1208" → "120°")
5. **ตรวจท่าไม่ตรงโฟลเดอร์:** ถ้า LLM บอกว่าเอกสารเป็นท่าอื่น (`is_exercise_mismatch`) → ย้ายผลไป `excluded_from_kb/` เป็นไฟล์ `_mismatch.json`
6. **บันทึกผล** เป็น JSON ใน `curated_data_v5/<ท่า>/`

### 2.3 ผลการทดสอบ

**(ก) ผลผลิตของ curator รอบ v5** (นับจาก `curated_data_v5/` วันนี้)

| ท่า | ช่วงที่ผ่าน | principle | mistake | finding | consequence | รวม | มี tag อาการ |
|---|---|---|---|---|---|---|---|
| Squat | 84 | 281 | 165 | 209 | 174 | 829 | 279 (34%) |
| Lunge | 80 | 234 | 74 | 256 | 91 | 655 | 189 (29%) |
| Push-up | 31 | 91 | 23 | 73 | 23 | 210 | 44 (21%) |
| Bicep curl | 34 | 75 | 27 | 81 | 20 | 203 | 71 (35%) |
| **รวม** | **229** | **681** | **289** | **619** | **308** | **1,897** | **583 (31%)** |

## ขั้น 3: Ingest เข้าฐานข้อมูลเวกเตอร์ (Embedding & Indexing)

### 3.1 เป้าหมาย
เก็บความรู้ในรูปที่ **ค้นด้วยความหมายได้** ไม่ต้องตรงคำ และกรองด้วยป้ายกำกับได้

### 3.2 ขั้นตอน (`ingest.py`)
1. **1 ประโยค = 1 ชิ้น (chunk):** แต่ละประโยคจากขั้น 2 เป็น 1 ชิ้น พร้อมป้ายกำกับ (metadata): ท่า (จากชื่อโฟลเดอร์) · kind · tag อาการ · แหล่งที่มา
2. **ตัดชิ้นซ้ำ:** สร้าง id จาก hash (MD5) ของเนื้อหา ชิ้นที่เหมือนกันเก็บครั้งเดียว
3. **แปลงเป็นเวกเตอร์:** `gemini-embedding-2` (ตั้งค่าที่เดียวใน `embedding_config.py`)
4. **เก็บลง PostgreSQL + pgvector** (รันใน Docker) ส่งทีละ 100 ชิ้น ถ้าชน rate limit จะรอแล้วลองใหม่
5. **แยก collection ตามเวอร์ชัน:** KB ใหม่เก็บ collection ใหม่ ไม่ทับของเดิม เพื่อเทียบผลย้อนหลังได้

| collection | embedding | ชิ้น | สถานะ |
|---|---|---|---|
| `kb_local_curated_v4` | MiniLM (`all-MiniLM-L6-v2`, รันในเครื่อง) | 2,348 | เก็บไว้เทียบ |
| `kb_gemini_curated_v4` | Gemini | 2,348 | เก็บไว้เทียบ |
| **`kb_gemini_curated_v5`** | **Gemini** | **1,897** | **ใช้อยู่** |

### 3.3 ผลการทดสอบ

**(ก) ความครบของข้อมูล**

| รอบ | ผล |
|---|---|
| v4 Gemini | 2,432 ชิ้น 241 แหล่ง เท่ากับ v4 MiniLM ทุกชิ้น (ข้อมูลต้นทางเดียวกัน เปลี่ยนแค่ embedding) → หลังถอด grokipedia เหลือ 2,348 ชิ้นทั้งสอง collection |
| v5 | 43 ไฟล์ 239 ช่วง 1,955 ชิ้น เข้าครบ 100% ไม่มี error → หลังถอดงานวิจัย preacher/incline เหลือ 1,897 ชิ้น |

**(ข) เลือก embedding: MiniLM เทียบกับ Gemini** (KB v4, golden set)

| mode | embedding | hit | kept | good | bad | neutral | precision |
|---|---|---|---|---|---|---|---|
| single | MiniLM | 9/10 | 47 | 33 | 9 | 5 | 0.70 |
| single | **Gemini** | 8/10 | 62 | 23 | **2** | 37 | 0.37 |

**(ค) สิ่งที่ลองแล้วไม่ใช้:** ใส่หัวบอกท่าและ kind ไว้หน้าประโยคก่อน embed (เช่น `[squat | mistake] …`) ทำให้ระยะเลื่อนทั้งกระดานจนเกณฑ์เดิมใช้ไม่ได้ และซ้ำกับการกรองด้วย metadata อยู่แล้ว จึงถอดออก

### 3.4 ข้อจำกัดและงานค้าง
- **เปลี่ยน embedding แล้วต้องตั้งเกณฑ์ขั้น 4 ใหม่:** ระยะของ Gemini อยู่คนละสเกลกับ MiniLM ตัวเลขข้ามช่วงจึงเทียบกันตรง ๆ ไม่ได้
- **`ingest.py` ไม่ลบแถวเก่าให้เอง** เมื่อแก้ป้ายกำกับของชิ้นเดิม ต้องลบแถวเก่าแล้ว ingest ใหม่

## ขั้น 4: ค้นคืนและคัดเลือกบริบท (Retrieval & Context Selection)

### 4.1 เป้าหมาย
จากผลตรวจท่า เลือกชิ้นความรู้ที่ **ตรงอาการ** และ **ครอบคลุมทั้ง "ผิดยังไง / ทำไมสำคัญ / แก้ยังไง"** ส่งให้ LLM ไม่เกินอาการละ 9 ชิ้น

### 4.2 ขั้นตอน

**4.1 รับผลตรวจท่า (Input Parsing)**
- ข้อมูลจากระบบ 1 เป็น JSON: 10 rep, rep ไหนถูกหรือผิด, ชื่ออาการ (`error_type`), คะแนน, ผลครั้งก่อน
- ตอนนี้ยังไม่ได้ต่อกับระบบ 1 จริง ใช้ข้อมูลจำลอง `mock_data/mock_sessions_per_fault.json`: 11 session (10 อาการ อาการละ 1 session + push-up ที่ไม่มีท่าผิด 1 session) ทุก session ผิด 4 จาก 10 rep โดยสลับตำแหน่ง rep ที่ผิด เพื่อตรวจว่า LLM อ่านข้อมูล rep จริง

**4.2 แปลงชื่ออาการเป็นคำค้น (Query Expansion)** (`error_taxonomy.py`)
- เปลี่ยนชื่อสั้นเป็นประโยคบรรยายอาการที่ใช้ภาษาเดียวกับ KB
  `Butt wink` → *"Lumbar flexion (butt wink): posterior pelvic tilt and rounding of the lower back at the bottom of the squat"*
- เหตุผล: ค้นด้วยชื่อดิบแล้วบางอาการหาไม่เจอ หรือเจอแต่ผิด

**4.3 ค้นหลายมุม (Multi-query Retrieval, R4)**
ต่อ 1 อาการ สร้าง 3 คำค้น:

| มุม | คำค้น | ตั้งใจให้เจอ |
|---|---|---|
| what: ผิดยังไง | คำค้นจาก 4.2 | `mistake` |
| why: ทำไมสำคัญ | *"Harmful consequences, injury risk and joint stress caused by: "* + คำค้นจาก 4.2 | `consequence`, `finding` |
| fix: แก้ยังไง | *"How to correct it, coaching cues and corrective exercises for: "* + คำค้นจาก 4.2 | `principle` |

แต่ละคำค้นค้นแยกตาม kind (kind ละ 12 ผู้สมัคร) กรองเฉพาะท่าเดียวกัน และเฉพาะชิ้นที่มี tag อาการนั้น (ถ้าอาการนั้นมีชิ้นที่ติด tag)

**4.4 คัดกรองผลค้น (Filtering / Gating)**

| ด่าน | เกณฑ์ | ค่าที่ใช้ |
|---|---|---|
| ใกล้พอ (absolute) | ระยะไม่เกินค่าสูงสุด | ≤ 0.40 ทุก kind |
| ใกล้พอ (relative) | ห่างจากชิ้นที่ดีที่สุด **ของคำค้นนั้น** ไม่เกิน | 0.03 |
| ไม่ซ้ำ | คำซ้ำกันเกิน (Jaccard) ถือว่าซ้ำ เก็บชิ้นเดียว | 0.72 |
| โควตาต่อ kind | จำนวนสูงสุดต่ออาการ | mistake 3 · finding 2 · principle 2 · consequence 2 = **9** |

**4.5 จัดรูป context (Context Assembly)**
- ใส่หัวให้แต่ละชิ้น เช่น `[finding | re: Knee valgus | source: TheBackSquat]` + ประโยค
- ถ้า session ไม่มีท่าผิด → ค้น "หลักการทำท่าที่ถูก" แทน

### 4.6 ผลการทดสอบ

ขั้นนี้มีไม้บรรทัด 2 อัน:
- **Golden set** (`eval/golden_chunks.json`): เฉลยว่าแต่ละอาการ "ควรได้" (`must_hit`) และ "ห้ามได้" (`must_not_hit`) ข้อความแบบไหน Claude เป็นผู้ติดป้าย
- **Relevance pool** (`eval/relevance_pool.json`): LLM อีกตัว (`gemini-3.8-flash`) ติดป้าย 1,256 ผู้สมัครว่าเกี่ยวกับอาการไหน ได้ข้อมูลที่เกี่ยวข้อง **411 ชิ้น** ใช้เป็นตัวหารของ recall

| ตัววัด | ความหมาย | ทิศที่ดี |

| precision | ชิ้นที่ตรงเฉลย ÷ ชิ้นที่ส่งให้ LLM | สูง |

| recall | ดึงข้อมูลที่เกี่ยวข้องได้กี่ส่วนจาก 411 | สูง |
| ceiling | recall สูงสุดที่เป็นไปได้เมื่อส่งได้อาการละ 9 ชิ้น = 0.21 | ใช้อ่านประกอบ |

### 4.7 ข้อจำกัดและงานค้าง
- **คำค้นถูกจูนเข้าหา KB:** Claude เขียนคำค้นโดยเปิดดู KB ไปด้วย และคนจูนกับคนให้คะแนน golden set เป็นฝ่ายเดียวกัน ตัวเลข 10/10 จึงเป็นค่าที่มองโลกในแง่ดี
- **อาจตีความอาการผิดตั้งแต่ต้น:** เช่น กฎของระบบ 1 ที่พูดถึงเข่าเลื่อนไปข้างหน้า แต่คำค้นเขียนเป็นเข่าล้มเข้าใน (knee valgus) ถ้าผิดจริง การวัดผลจะจับไม่ได้ รอ `form_rules.py` จากทีมระบบ 1 หรือให้ PT ยืนยัน
- **Golden set จับคู่ด้วยข้อความตรงตัว:** พอ KB ใช้คำเปลี่ยน ตัวเลขก็เพี้ยน ต้องเพิ่มถ้อยคำเมื่อ KB เปลี่ยน
- **Relevance pool ติดป้ายโดย LLM** ยังไม่มีคนสุ่มตรวจเทียบ และประโยคที่เขียนต่างกันแต่ความหมายเดียวกันถูกนับเป็นหลายชิ้น recall จริงจึงสูงกว่าที่วัดได้ (แต่ยังเทียบระหว่างขั้นได้ เพราะตัวหารเท่ากัน)
- **เกณฑ์ขั้น 4.4 ยังไม่ได้ sweep ใหม่บน KB v5** ใช้ค่าที่ sweep บน KB v4

## ขั้น 5: สร้างคำแนะนำด้วย LLM (Feedback Generation)

### 5.1 เป้าหมาย
เขียน feedback เป็นภาษาโค้ชที่คนทั่วไปอ่านเข้าใจ บอกว่า **ผิดอะไร · ทำไมสำคัญ · แก้ยังไง · ครั้งหน้าทำอะไร** โดยใช้ข้อมูลจาก KB และไม่แต่งข้อมูลเพิ่ม

### 5.2 ขั้นตอน
1. **รวม input:** ผลตรวจท่า (JSON) + context จากขั้น 4
2. **เรียก LLM:** `gemini-3.5-flash-lite` ที่ temperature 0.7 (ภาษาเป็นธรรมชาติ คงค่านี้ไว้ทุกรอบเพื่อเทียบข้ามรอบได้)
3. **prompt v11** สั่งให้เขียนตามโครง:
   - ความคืบหน้าเทียบกับครั้งก่อน
   - ต่ออาการ: คืออะไร · ทำไมสำคัญ · วิธีแก้ 4 แบบที่ไม่ซ้ำกัน (คำนึกระหว่างทำ, ปรับ setup, ท่าฝึกแก้, วิธีเช็กตัวเอง) · rep ไหนที่ผิด
   - แผนครั้งหน้า 2–3 ข้อ
4. **กฎสำคัญใน prompt:**
   - ห้ามแต่งตัวเลขหรือแหล่งที่ไม่มีใน context
   - ต้องแปลศัพท์เทคนิคเป็นภาษาคนทั่วไป ห้ามลอกประโยคจากงานวิจัย (ตัวเลขต้องตรง แต่ประโยคไม่ต้องลอก)
   - ตัวอย่างใน prompt ต้องเป็นเรื่องนอกงานจริง (ข้อมือ คอ เวลาพัก) ไม่อย่างนั้นทั้ง RAG และ no-RAG จะได้คำอธิบายสำเร็จรูปจาก prompt
5. **สร้างคำตอบ no-RAG คู่กัน** (prompt เดียวกันแต่ไม่มี context) เพื่อเทียบ
6. **บันทึกรายงาน** ใน `compare_output/*.md` และ `.json`: ค่าที่ตั้ง, ตัวเลขการค้น, context ที่ส่งจริง, คำตอบ RAG และ no-RAG วางคู่กัน

### 5.3 ผลการทดสอบ

**(ก) ตัวเลขอัตโนมัติ** (`eval/eval_generation.py`, mock 4 session)
- **unglossed jargon:** ศัพท์เทคนิคที่ใช้โดยไม่อธิบายภายใน 120 ตัวอักษร (เช็กแค่ว่ามีคำอธิบาย ไม่ได้เช็กว่าอธิบายถูก)
- **longest shared n-gram:** ประโยคที่ลอกจาก context ยาวสุดกี่คำติดกัน (no-RAG ไม่เคยเห็น context ตัวเลขของ no-RAG จึงเป็นเส้นฐานของความบังเอิญ)

| prompt | ฝั่ง | ศัพท์ไม่อธิบาย | ลอกยาวสุด (คำ) | ช่วงที่ลอก ≥ 6 คำ |
|---|---|---|---|---|
| v9 | RAG | 17 | 20 | 13 |
| v9 | no-RAG | 3 | 6 | 1 |
| **v10** | **RAG** | **1** | **9** | **3** |
| v10 | no-RAG | 0 | 6 | 1 |

สิ่งที่เหลือใน v10: ศัพท์ 1 คำคือ "center of mass" (lunge) · ลอก 9 คำคือ "2 to 3 cm short of contacting the ground" ซึ่งเป็นตัวเลขเป้าหมายที่ตั้งใจให้คงไว้

**ตัวอย่างการแปลศัพท์** (ข้อมูลเดียวกันจาก KB)

| อาการ | ก่อน (v9) | หลัง (v12/v13) |
|---|---|---|
| Lunge ตัวโน้มหน้า | *"…onto your hip extensors and ankle plantar flexors … knee extensors"* | *"…onto your hips and calves while taking the load off your quads"* |
| Squat ย่อไม่ถึง | *"…gluteus muscular complex may not be adequately challenged"* | *"your glutes and the backs of your thighs don't get fully challenged"* |
| Bicep curl ศอกไหล | (KB) *"the biceps brachii is a biarticular muscle"* | *"your biceps cross both your elbow and your shoulder joint"* |

**(ข) ประโยคผิดในคำตอบ: prompt v6 → v7** (11 ก.ย., 4 session, Claude อ่านตรวจ)

| ตัววัด | v6 | v7 |
|---|---|---|
| ประโยคที่ยืนยันข้อมูลผิด | 4 (momentum, incline bench, back-knee rotation, "1208") | 0 (มี 1 ประโยคที่พูดแบบไม่ฟันธง เพราะ KB ไม่มีข้อมูล back knee) |
| session ที่วิธีแก้อ้างหลักการจาก KB | 0/3 | 3/3 |

**(ค) อ่านเทียบ RAG กับ no-RAG รอบ v13** (26 ก.ย., 11 session, 1 คำตอบต่อ session)

| ผล | อาการ |
|---|---|
| RAG ชนะชัด | squat butt wink · push-up partial ROM · bicep elbow flare |
| RAG ถูกทาง แต่ใช้ผลวิจัยผิดเงื่อนไข | lunge shallow lunge (ความยาวก้าวถูกใช้เป็นเรื่องความลึก) |
| RAG ใช้ข้อมูลผิดเงื่อนไข | squat knee valgus (ผลการทดสอบ "วางแผ่นรองส้น 2 นิ้ว" กลายเป็นคำแนะนำให้ทำทุกเซ็ต) · push-up hip sag (แรงกดหลัง 1,838 N ของท่าปกติถูกอ้างเป็นผลของสะโพกตก) |
| no-RAG ดีกว่า | squat partial squat |
| เทียบไม่ได้ | lunge trunk lean (ฝั่ง no-RAG error ตอนเรียก API) |

ตัวอย่างที่ RAG ชนะ: Butt wink ฝั่ง no-RAG แนะนำให้ลดความลึก ส่วน RAG แนะนำให้ยืนกว้างขึ้นและให้เข่าบานออก ซึ่งแก้ที่ต้นเหตุ

> ผลข้อ (ค) ใช้เป็นตัวอย่างประกอบเท่านั้น สรุปเป็นสถิติไม่ได้ เพราะ temperature 0.7 ทำให้คำตอบต่างกันทุกครั้งที่รัน

**(ง) LLM ผู้ตัดสินแบบไม่รู้ที่มา (Checkpoint G1): เครื่องมือเสร็จ ยังไม่มีผล**

| ส่วน | รายละเอียด |
|---|---|
| วิธี | สร้างคำตอบ 5 รอบต่อ session ให้ `gemini-3.8-flash` (temperature 0) เทียบคู่คำตอบโดยสลับซ้ายขวาแบบสุ่ม |
| เกณฑ์ (ตาม SportsGPT) | Accuracy · Comprehensiveness · Professionalism · Feasibility · overall |
| สถิติ | sign test ของ overall 50 คู่ (10 session × 5 รอบ) ต้อง p < 0.05 |
| ตัวควบคุม | session ที่ไม่มีท่าผิด context เหมือนกันทั้งสองฝั่ง ควรออกใกล้ 50:50 · ตรวจว่าผู้ตัดสินเลือกฝั่งซ้ายหรือขวาบ่อยเกินไหม |
| ผู้ตัดสิน 2 แบบ | ไม่เห็นหลักฐานจาก KB กับเห็นหลักฐาน (smoke test: ผู้ตัดสินที่ไม่เห็นหลักฐานมองว่า "แผ่นรองส้น 2 นิ้ว" ไม่สมจริงและให้ฝั่งเก่าชนะ 2/2) |
| สถานะ | รออนุมัติค่า API (สร้างคำตอบ 110 ครั้ง + ตัดสิน 110 ครั้ง ประมาณ 1 ชั่วโมง) |

ตัวเลขอ้างอิงจากงานอื่น: SportsGPT ตัด RAG ออกแล้ว Feasibility ตกจาก 3.9 เหลือ 1.65 ขณะที่ Accuracy แทบไม่ตก แปลว่า RAG ชนะเมื่อให้ความรู้เชิงปฏิบัติที่มีตัวเลข

### 5.4 ข้อจำกัดและงานค้าง
- **ยังไม่มีหลักฐานเชิงสถิติว่า RAG ดีกว่า no-RAG** ต้องรัน G1
- **ต้นเหตุที่ RAG ยังไม่ชนะชัด:** KB มีแต่สิ่งที่ LLM รู้อยู่แล้ว (นิยามอาการ ผลวิจัยทั่วไป) ขาดท่าฝึกแก้ ปริมาณการฝึก และสาเหตุ → วิธีแก้ (กลับไปแก้ที่ขั้น 1–2)
- **LLM ใช้ผลวิจัยผิดเงื่อนไข** (3 เคสในรอบ v13) แผนถัดไป (ขั้น P): สั่งใน prompt ให้คงเงื่อนไขของผลวิจัย และปริมาณการฝึกต้องมาจากตำรา
- **ตัววัดศัพท์เช็กแค่ว่ามีคำอธิบาย ไม่ได้เช็กว่าถูก** ทางแก้: ดึงคู่ "ศัพท์ → คำแปล" ให้ PT ตรวจ
- **ยังไม่ได้รัน `eval_generation.py` บน prompt v11–v13** (ไม่เสียค่า API รันได้ทันที)
- **ผู้ตัดสินเป็น Gemini ตระกูลเดียวกับตัวสร้างคำตอบ** เพราะมี API key แค่ของ Gemini

## ภาคผนวก: คำศัพท์

| คำ | ความหมาย |
|---|---|
| RAG | ให้ LLM ค้นตำราก่อนตอบ (Retrieval-Augmented Generation) |
| KB | Knowledge Base: ตำราที่เตรียมไว้ |
| window / ช่วง | ส่วนของเอกสารที่ตัดส่งให้ curator ครั้งละ 6,000 ตัวอักษร |
| chunk / ชิ้น | ข้อมูล 1 ชิ้นใน KB (1 ประโยค) |
| kind | ประเภทของชิ้น: mistake / finding / principle / consequence |
| tag อาการ | ป้ายบอกว่าประโยคนี้พูดถึงอาการไหน (`applies_to_fault`) |
| embedding / เวกเตอร์ | ตัวเลขแทนความหมายของประโยค ใช้ค้นด้วยความหมาย |
| query expansion | ขยายชื่ออาการสั้น ๆ เป็นคำค้นที่ใช้ภาษาเดียวกับเอกสาร |
| multi-query | ค้นหลายคำค้นต่อ 1 อาการแล้วรวมผล (R4 = what / why / fix) |
| gate | ด่านคัดกรองว่าชิ้นไหนได้เข้า context |
| context | ชิ้นที่คัดแล้วส่งให้ LLM (อาการละไม่เกิน 9 ชิ้น) |
| golden set | ชุดเฉลยว่าอาการไหนควรได้หรือห้ามได้ข้อมูลแบบไหน |
| relevance pool | ชุดข้อมูลที่ LLM ตรวจแล้วว่าเกี่ยวกับอาการไหน (411 ชิ้น) |
| recall / precision | ดึงของที่ควรได้มาได้กี่ส่วน / ของที่ดึงมาถูกกี่ส่วน |
| ablation | ทดลองเปลี่ยนทีละอย่างเพื่อดูผลของแต่ละอย่าง |
| temperature | ความสุ่มของ LLM (0 = ตอบเหมือนเดิม, 0.7 = ตอบต่างกันทุกครั้ง) |
